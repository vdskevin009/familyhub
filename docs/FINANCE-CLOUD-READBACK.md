# Cloud Finances capture readback (local candidate)

This adapter performs **no Finances collection and no production writes**. Finances is available only to the assistant's cloud tools. The local CLI uses actual paired FamilyHub GET routes and existing stores; it does not invent a native Finances endpoint. Source archives and manifests stay in a private evidence directory outside Git. No runtime module registration, installer, public UI or schedule changes are included.

## Reviewed private scope before admission

Keep `finance-feed/daily-scope.json` with schema 1, accountPolicy `all-linked`, mappingDigest (SHA256 of the exact private mapping file), one required period, and subjects:
- collection: accounts, transactions, investment_holdings, investment_transactions, recurring_transactions, liabilities.
- accounts, balances and transactions: each `["all-linked-source-universe"]`.
- contributions: the actual existing plan IDs.

The scope binds the all-linked policy before calling cloud tools. Complete raw linked-account enumeration establishes the current universe, not the previous list of accounts. Every query and retained account-enumeration metadata set must match that universe exactly. Accounts with zero transaction rows remain covered by a complete exhaustive query; the verifier never requires one transaction per linked account. Unmapped new accounts remain source-native. Historical mapping entries absent from the current universe are preserved and do not expand it. Mapping JSON is `{ "fsi_<source-key>": "existing-ledger-account-id" }`, prepared only from previously attested identities, never names, amounts or suffixes. Its exact bytes/hash are reviewed before begin. The current adapter requires existing mapped-account IDs to remain in the baseline ledger.

## Sequence and exact file contract

1. Run `FinanceScheduledBridge.mjs scheduled-begin <dataDir>` before any cloud source or FamilyHub API calls. On skip, STOP. The admission file/token is private. No clock override exists in the CLI.
2. Run `FinanceCloudReadback.mjs baseline <dataDir> <evidenceDir> <admissionFile>`. It GETs ledger, inventory, expenses and Contributions, compares actual local stores/projection, and saves immutable `baseline-<attemptId>.json` before collection or intake. Record its SHA256 in the manifest. This command writes only its private proof file, never production state.
3. Check admission immediately before each cloud call. Preserve entire native responses and full exports, not previews. A private controller creates normalized capture files after admission. Every capture must have a true `collectedAt` between baseline capture and admission deadline; this is receipt time, not source freshness. Archive a second, byte-identical copy at a distinct real path and verify SHA256/readback. Baseline or old captures cannot be reused as today's collection.
4. Perform separately authorized intake using existing preview/revision/apply protections. Before each mutation use the bridge intent journal, and never replay an uncertain POST. This adapter neither imports a transaction nor changes Contributions configuration. Save current source inventory and expenses through their existing APIs; mapped balance observations use their existing supported import. Real orchestration remains a separate integration step.
5. Create the manifest below, then run `FinanceCloudReadback.mjs report <dataDir> <evidenceDir> <admissionFile> <manifestFile>`. It derives all five receipts from fresh independent GET/file reads and saves the private report. Add `reportFile` (basename returned) to the manifest.
6. Run the same CLI with `finalize`. Finalization reloads its read-only verifier only after token/window admission, recomputes proofs from archives and actual stores, and passes the result to the bridge. It never trusts report status/digests alone. An already-finalized exact replay verifies local proof without API calls.

Each `PrivateRef` is `{path,sha256}`, relative to evidenceDir. Resolution rejects path traversal and symlink escape. Each `RawCapture` is `{capture:PrivateRef,archive:PrivateRef}` with distinct real files and identical bytes. Private directories must be outside any repository. The CLI logs only generic status and private artifact filename, never tokens, accounts, amounts or pairing credentials.

Manifest (`FinanceCloudManifest` in source):
- schema 1, attemptId, scopeDigest, baseline PrivateRef, mapping PrivateRef.
- linked RawCapture: JSON `{collectedAt,rawLinkedAccounts:<full tool response>}`. Original structuredContent.institutions/account_coverage and accounts are retained. Manual account enumeration is currently unsupported and makes enumeration incomplete, never silently complete.
- expenses RawCapture: existing `SourceExpensesEvidence` `{collectedAt,accounts:[{item_id,account_id,name}],transactions:{query,pages}}`. All source transaction fields remain in each page; no select_fields or predicate narrowing allowed. The date range equals the single reviewed period and covers every Contributions plan through its evaluated date.
- nativeTransactions: one NativePage binding per normalized transaction page, in order.
- sections: exactly four entries `{dataset,raw:RawCapture,nativePages:NativePage[]}`. Raw JSON is `{collectedAt,query,pages}` with original metadata and all items. Explicit cursor chains must match, with no selected fields or filters narrowing source coverage.
- inventory: PrivateRef to the exact prepared source-inventory snapshot saved in the real sidecar.
- optional reportFile basename for the finalization CLI.

NativePage is `{response:RawCapture,resultIndex:number,export?:RawCapture & {sourceFileId:string}}`. The full native tool response must contain structuredContent.results with exactly one matching index/query_type and is_error false. Inline items and all result metadata must equal the normalized result. For CSV, export.sourceFileId must equal the native result.file_id; original CSV bytes and envelope are archived, row count must equal result_count, and normalized items must exactly equal `parseNativeFinanceCsv(originalBytes)`. Preserve ALL original result fields when adding parsed items. Preview rows never substitute for the export. The parser handles quoting, multiline cells, signed amounts, pending boolean, flattened category fields and optional pending identity; it retains other original fields. CSV blanks cannot distinguish absent/null/empty; this limitation stays explicit and original bytes remain authoritative. Unsupported export formats/field encodings fail closed, without repair or fallback.

## Receipt semantics and current limitations

The verifier independently reads real `/finances`, `/finance/source-inventory`, `/finance/source-expenses`, `/contributions/progress`; compares them to local stores and recomputed Contributions; re-derives expense snapshots from native-bound evidence; verifies every current mapped or unmapped balance; preserves all prior ledger facts, decisions, balance history, import history and expense captures. Mapping/config changes or mismatched snapshots block. Account names/keys and source amounts are checked; no account is inferred. Source-as-of remains unknown in this adapter's current undated-balance path; dated balances require an explicitly reviewed extension rather than timestamp invention.

Complete native source persistence, including new unassigned identities, can satisfy transaction and Contributions stages even though canonical attribution remains unchanged. Contributions is a verified no-op projection plus complete raw source retained separately, NOT an assertion that new payments were attributed or tax rights established. The stage is marked partial if the transaction source coverage is incomplete. Other datasets lacking coverage make collection partial but do not invalidate independently verified balances/transactions. Empty holdings/activity/liabilities without coverage are unavailable, never attested zero. All five stages must be confirmed for scheduled daily success.

The producer trusts the authorized cloud controller to capture authentic responses and honest capture timestamps; hashes do not authenticate a malicious local actor. Persistent filesystem lock semantics, operator-established crash recovery, no automatic stale lock stealing, uncertain write readback-only, and after-window notification responsibilities are in FINANCE-DAILY-GATE.md. Read-only recovery uses the existing capture/intent manifest, never a new collection. If no authoritative manifest can establish a not-applied outcome, stop for operator review; this adapter does not invent a no-write proof.

Remaining gates: reviewed private mapping/scope, real cloud controller, authorized real intake/readback, native CSV compatibility against a fresh capture, production clock-window admission, and automation activation. No current historical private capture is proof for a new scheduled attempt.

### Bounded inventory semantics verification

Inventory `collectedAt` must equal the maximum of the actual linked-account and four section capture timestamps, never an independently minted "fresh" time. Account kind and institution are derived from the native linked account type and owning institution name. Availability/status/counts are derived from each exact native page chain; missing coverage cannot be promoted to available. The mapped-account exclusion uses the existing preparation convention (partial account availability for the admitted subset).

Nonempty recurring forecast transformations and credit-field transformations are not yet independently supported. The verifier rejects changes to those unsupported fields relative to the baseline, rather than accepting a prepared JSON just because it was persisted. Preserved baseline fields remain explicitly unverified, with `verificationLimits` and partial accounts/collection stages. A completely covered empty native recurring/liability dataset can attest an empty corresponding field. Independent balances and transactions remain separately verifiable. Therefore existing nonempty forecasts or credit details can block global daily completion until their exact field-level derivation is implemented; this is a real integration limitation, not a reason to rewrite/drop them.
