Status: In progress, local opt-in implementation candidate; production remains unchanged. Phase 3 below supersedes historical foundation-only/runtime/cache-pending statements. ## Accepted scope

Move all Gmail retrieval for the requested account to the connected Gmail plugin, following the existing connector direction. Preserve ordinary invoices, Important Mail, Blue Cross emailed tables, complete PC Express MIME, history/repair coverage, source account/message/thread/attachment identities, original attachments, deduplication, manual corrections and reimbursement history. Reuse the existing classification/reconciliation code; the healthcare-PDF-only `/invoices/import-connector` endpoint is not an all-mail replacement. This requirement is not yet implemented end to end.

## Local implementation

`apps/worker/src/gmail-plugin-batch.ts` has two pure in-memory boundaries:

- `pluginMessageToRawMail(unknown)` converts the observed Gmail plugin snake_case full-message structure into existing `RawMail`. It retains MIME headers, labels, source timestamp and source IDs. Encoded bytes require canonical base64url and exact declared byte length. Decoded content is re-encoded as UTF-8 only when its byte length matches the original declaration. When both representations exist they must agree. Summaries/snippets are never content substitutes. Recursive multipart and external attachment references are preserved; a missing internet Message-ID remains missing.
- `createPluginBatchTransport(unknown, expectedAccount)` validates an entire same-account batch before exposing a `GmailCall`. Its token is a random local batch handle, not OAuth credentials. Exact query/page-size matching replays fully enumerated page chains; unknown queries, missing pages/messages/attachments, duplicates, invalid sizes or a different handle reject. Responses are isolated copies. It makes no network requests, stores no credentials, writes no coverage, and never falls back to Google.

Input schema: `{schema:1, account, messages:RawMail[], attachments:[{messageId, attachmentId, size, data}], queries:[{q,maxResults,complete:true,pages:[{pageToken?,messageIds,nextPageToken?}]}]}`. Data is original base64url bytes. The first query page has no input token; each following page consumes the preceding next token; only the terminal page omits its next token. Order is preserved, not sorted. Query text is matched exactly, not evaluated locally or replaced by a broader inferred search. An explicitly complete empty result is different from a missing query.

Limits: 64 MB serialized batch, 500 messages, 1,000 attachment records, 20 queries, 100 pages/query, 50 IDs/page, 200 MIME parts/message, depth 12, 30 attachments/message and 20 MB per body/attachment. Message/thread IDs are at most 200 characters; attachment IDs at most 1,500. Larger or unsupported evidence stops; it is never clipped to fit. Current parsers do not consume external unnamed text bodies or named inline attachment bytes; the adapter refuses those shapes rather than silently dropping them. From/Subject must be unambiguous; malformed dates and missing labels are rejected. Downstream attachment extraction still has its existing 10 MB and supported-format limits and review states.

The batch is a contract for a future trusted orchestrator, not independent proof of mailbox completeness. `complete:true` cannot prove an upstream plugin search was exhaustive. The orchestrator must actually enumerate all returned pages for the exact frozen query and verify source-account binding. A capped search, truncated tool response, guessed date window, absent continuation token caused by display truncation, or a single matching message is not complete evidence. This foundation does not invent Gmail queries or report coverage.

## Required orchestration and cutover gates

1. Discover and bind the connected source account, without extracting plugin credentials or introducing fake `GmailAccount` secrets. Obtain frozen invoice, history, repair, retry and grocery query requests from collector state. Some existing repair queries lack an upper date bound; explicitly handle them rather than claiming this module bounds those searches.
2. Read every exact query page through the plugin, preserving opaque pagination. Convert complete MIME and download original attachment bytes. Plugin `read_attachment` extracted-text previews, including previews marked truncated, are not attachment bytes. Verify the downloaded original length and source reference. Add a supported authenticated private intake/orchestration boundary with schema, replay, concurrency and recovery controls; none exists here.
3. Inject the transport into the existing invoice/Important Mail, historical/repair, Blue Cross-email and grocery paths without replacing classification. Missing evidence must not advance checkpoints or replace a prior successful scan. Validate actual collector integration and restart/repeated-run behavior before changing sources.
4. Cover all consumers, including `collectInvoices`, `GroceryCollection`, `importBlueCrossMessages`, `invoiceAttachment`, credential-derived setup/status, and retry reads. Original attachment downloads after a batch expires require a durable private byte cache for supported types or a supported on-demand plugin route. Existing connector PDF-only storage is insufficient. The new batch is ephemeral and does not provide that persistence.
5. Decide the unpaired browser Gmail fallback (`apps/web/src/google.ts`) migration explicitly. Separate user-initiated Drive upload and Google login must not be removed merely because Gmail retrieval changes.
6. Compare source IDs and expected outputs across all streams in a read-only/dry-run parity check. Test manual corrections, stable dedup, original attachment retrieval, complete versus partial/error coverage, history resume, and interrupted/repeated runs. Existing regression tests remain necessary but do not prove live parity.
7. Coordinate the existing invoice/grocery daily runner with the separate connector workflow; no second competing schedule. Deployment, security-pin review, source selection, rollback and first natural scheduled run are separate gates. Do not silently alter a pinned worker hash or stop a working path before parity and recovery are verified.

No live import, production migration, portal operation, automation change, publication, security change or completed coverage is claimed by the foundation tests.

## Phase 3: opt-in worker lifecycle and original retrieval (local candidate)

This section supersedes phase-1/2 statements that runtime orchestration and cache callers are absent. No production activation or deployment is implied.

`mail-collection-runtime.ts` now owns the existing paired invoice, grocery and manual Blue Cross triggers from initial planning through separate plugin retrieval, cache validation and collector application. It takes fresh immutable plans for every bounded continuation. A shared busy lock covers retrieval as well as application; abort/timeout waits for runner shutdown and cannot apply late evidence. A pre-apply failure says checkpoints were not advanced; an applying failure explicitly allows for already-saved verified pages. Missing final status persistence cannot look like an unqualified success. Restarted interrupted runs retain an error rather than claiming completion.

The separate `gmail-plugin-runner.ts` invokes bounded, ephemeral, read-only CLI sessions for exact permitted Gmail operations and uses actual completed MCP structured results, never model final text. It verifies account binding through the connected profile, enumerates exact complete query chains, retains source MIME and downloads original attachment bytes rather than extracted previews. It validates effective configuration and disables unrelated applications/tools/plugins per invocation. The existing private classifier remains isolated with apps/MCP disabled. Retrieval bounds and unsupported source formats stop the attempt without narrowing its requested query or certifying partial coverage. Current limits are 200 unique messages, 20 total search pages, 100 tool calls, 64 MB tool output, 40 MB original bytes and 20 MB per attachment, with a 120-second per-call limit and a 15-minute runner limit. The worker lifecycle enforces a tighter 12-minute retrieval deadline across all configured accounts. These are maximum limits, not promised throughput: the final isolated CLI probes observed roughly 36–42 seconds per tool invocation including configuration/profile checks (earlier simpler probes were near 20 seconds). Current-window acceptance must record exact call counts and elapsed time. A normal complete window that cannot finish inside the effective deadline is a cutover blocker; do not silently shrink its query or discard attachment evidence. Only an observed, exact original-file host is allowed; other hosts require review rather than a broader wildcard.

All validated original attachment leaves are cached before collector application, including known/manual-authority records, Blue Cross messages, unsupported extraction types and grocery-only results. A source conflict or cache failure blocks application. Existing `invoiceAttachment` callers, including claim preparation and paired downloads, use exact original cache identities in plugin mode and a source-bound on-demand plugin read on a miss. No ledger attachment schema migration is required. Manual Blue Cross intake uses the same configured source and original-byte validation. Full mail bodies remain transient; original attachment bytes and minimal identity manifests are private durable worker data when plugin mode is selected.

### Explicit source selection and readiness

`mail-source-policy.json` is a private operator-managed file; this change does not create one. Supported plugin shape: `{schema:1,mode:"plugin",accounts:[{email,label,linkId}]}`. Emails must be canonical lowercase and each link must match the supported `link_...` format. All explicitly configured accounts are planned/retrieved and applied together, not one at a time with a misleading global-success update. Before activation, compare the intended account set with existing active source identities and preserve independently scheduled connector intake; a valid JSON file is not evidence that every intended account was migrated.

The runtime records only a minimal durable `mail-source-selection.json` marker when it accepts explicit plugin selection. Missing policy is legacy only on never-selected installations. Missing/malformed policy after plugin selection fails closed, including after restart and for attachment downloads. An explicit local rollback policy `{schema:1,mode:"legacy",allowDirectGmail:true}` permits the old credential path; deleting the selected policy does not. Invalid runtime state is preserved, not silently overwritten. Source-policy changes during retrieval invalidate application. Corrected valid policies are revalidated safely, not silently replaced by OAuth.

The readiness CLI is read-only and reports `{mode,ready}` for configuration readiness, not a verified live connection. Source scripts consult it instead of unconditionally requiring a Gmail DPAPI file. The daily runner also checks authenticated worker source mode/readiness before collection, so an older already-running worker cannot silently use OAuth with a plugin-selected configuration. The existing schedule is not changed or reinstalled. Daily continuation uses the current worker's explicit readiness signal rather than a hardcoded historical repair version.

### Browser and Drive boundary

Authenticated snapshots expose source mode per account. Browser Gmail reads are blocked for accounts known to use the plugin, including after unpairing. Persisted markers contain only nonsecret account/source selection; storage failure preserves paired document viewing while restricting uncertain browser reads and displaying a warning. Worker-managed Drive archive obtains original bytes through the paired attachment endpoint before folder/upload work, with no browser Gmail fallback. Separate user-initiated Drive authorization/upload remains intact. An optional `VITE_MAIL_RETRIEVAL_MODE=plugin-only` deployment gate is implemented but unset; default behavior is unchanged for a fresh unpaired browser with no known source selection. Decide and validate that deployment gate before claiming that every browser surface is plugin-only.
