# Private PWA notifications

Requirements FH-NOTIF-001/002, Issue #170. Open the bell or Other → Notifications. Finances keeps its existing two tabs.

The paired worker records a private history and scans available saved evidence every 15 minutes while running. This scan never opens an insurer, signs in, imports statements, changes a classification or performs a financial action. The first successful read of each source is a silent baseline; existing records are visible in history without flooding devices. Up to 500 events are shown, with persistent deduplication identities. Repeated scans/restarts do not replay earlier events. Source outages are displayed and do not silently resolve existing alerts.

## Evidence rules

- Collection alerts use recorded error/login-required status, or an existing successful collection older than seven days. The freshness threshold is not proof that a schedule failed. Raw provider errors do not enter notifications.
- Reimbursement events require a manually confirmed match, or an automatic match scoring at least 90 on the existing 0–100 scale; unresolved, ignored and review-required evidence is excluded. A positive explicit source `ReimbursedAmount` and matching currency are required. The remaining recorded balance distinguishes partial reimbursement. An insurer statement does not prove the bank deposit.
- Unmatched records open the current reconciliation queue; already resolved or unavailable links say so. No automatic association occurs.
- Recurring-charge review leads require two posted, nonduplicate payments to the same labelled merchant/account/currency, 20–45 days apart, with an increase of at least **500 currency minor units (5 in CAD or USD) and 10%**. Currency values are never converted; this is a fixed minor-unit threshold in each source currency. Supported categories are subscriptions, communications and fees. The latest payment must be within 45 days. Payment changes can reflect tax, billing periods or adjustments; no guaranteed saving is calculated.
- Contract renewals, commitment ends and investment maturities use explicit stored dates, with 30-, 7- and 1-day windows in America/Vancouver. A promotion end also requires a manually entered source note. A duration alone never invents an end date. Contract editing/sharing retains the optional `promotionEnd` field and its source.
- The weekly summary covers the prior Monday–Sunday only when declared source dates and collection date span that week. Consumption nets classified refunds and excludes classified transfers, card repayments and investments; pending and duplicate candidates remain excluded. Each currency is separate, with unreviewed count and an explicit imported-source coverage limit. This is not a guaranteed household total or a spending target. Corrections update existing history without sending the same week again.

## Device setup

The history works without push credentials. Web Push is opt-in for each phone/browser and needs a running paired PC with outbound HTTPS access and a valid browser subscription. No email is sent.

1. Inspect existing FamilyHub setup with `node apps/worker/dist/notification-setup.js --status`, using the installation's existing `FAMILYHUB_WORKER_DATA`. The output is configuration status only. Existing explicit `FAMILYHUB_PUSH_PUBLIC_KEY` / `FAMILYHUB_PUSH_PRIVATE_KEY` environment settings take precedence; otherwise the worker reads `notifications-vapid.private.json` protected by the current Windows user's DPAPI. Never reuse another app's VAPID identity or print secrets.
2. Only after the operator approves creation of the persistent FamilyHub notification identity, run `node apps/worker/dist/notification-setup.js --create --operator-approved` with that same data directory. Startup, polling and HTTP requests never generate keys. An existing or unreadable identity is never automatically replaced. New setup is a separate action from installing the source code. Existing subscriptions depend on their identity; rotation needs a deliberate migration/re-enrollment plan.
3. On a compatible phone, open the installed PWA, then Notifications → Préférences → Activer sur cet appareil. The button requests permission directly from the user gesture. On iPhone/iPad, install the web app on the Home Screen first; Web Push for Home Screen web apps requires iOS/iPadOS 16.4 or later. Permission denied in OS/browser settings must be changed there by the user.
4. Send one test. **Accepted by the Push service** does not mean the device displayed it. Close/background the PWA and check the intended physical phone. Use **J'ai reçu la notification** only after observing it. The saved confirmation is the user's report, not an automatic delivery receipt. Tests are rate-limited to one per minute per device.

Shared preferences control future sends, not whether evidence is kept in history. Enabling a preference or enrolling a device does not replay old alerts. Each scan sends at most one generic update per enabled device, even after a large import. The lock screen shows only **FamilyHub — Une mise à jour est disponible** and an app icon. The encrypted payload contains an opaque event ID, never a person, provider, medical detail, transaction, amount or source-record ID. Full detail and linked records are fetched through the existing authenticated worker connection.

**Désactiver dans ce navigateur** unsubscribes locally. **Retirer cet appareil** removes the subscription from the PC; no subsequent send uses it. Expired subscriptions (HTTP 404/410) are disabled. A failed HTTP response is distinct from an uncertain response loss; neither causes an automatic replay. Re-enrollment is explicit. Push endpoints and subscription keys remain in the private worker store and never appear in its public snapshot, logs or repository.

## Limits and verification

A stopped/offline PC cannot send or report its own outage. The phone OS, network and push service may delay or suppress display. The in-app history needs the paired PC to load; an already loaded page retains its current history if a refresh fails. Source-derived alerts are only as complete as the imported records and manual review. No notification authorizes a purchase, claim, subscription change, financial transaction or provider contact.

Automated tests use synthetic finance/insurance records, ephemeral test keys, a real local service worker and mocked enrollment/delivery. They cover evidence thresholds, prior-source baseline, deduplication across restart, revisions, preference persistence, lost responses, expired devices, generic service-worker content, source links, authorization/origins, corrupted state and mobile layouts. No automated test contacts a real push provider or changes production credentials. Physical-device enrollment and closed-PWA receipt remain live acceptance gates until separately observed.
