# Source-native expenses (FH-FIN-025)

This separate view addresses current provider transactions without guessing mappings to historical FamilyHub accounts. It never imports source-native rows into the canonical ledger. Local implementation and synthetic tests are not deployment or private-source activation.

## Preparation and exact scope

Pure prepareSourceExpenses in apps/worker/src/finance-source-expenses-prepare.ts takes {collectedAt, accounts:[{item_id,account_id,name}], transactions:{query,pages:[{requestCursor,result}]}}. Accounts must be the explicitly selected linked source accounts, not name/amount/last-four matches to canonical accounts. The actual query must select transactions, account_id.in, date.between and include_transfers:true. Only limit, ordering and select_fields are additionally allowed. Amount/category/pending filters are rejected so a purchase-only or credit-only query cannot masquerade as general spending. Preserve the original query and page chain, rather than fabricating an expanded scope.

Raw provider amount is positive outflow and negative inflow. A supplied normalized_amount must be its inverse. Minimized rows retain date, description, currency, pending, nullable source category primary/detailed/confidence_level and whether a transfer_to_account_id or transfer_transaction_id was actually provided. Missing linkage stays unknown. Exact linked pending_transaction_id may suppress its pending predecessor when the posted row is present; no name/amount/date matching is performed. Identical provider identities within the query deduplicate; contradictory same-ID rows fail. Changes across later captures remain separate historical evidence, not duplicate expenses.

Account keys use fsi_ plus SHA256(JSON(['finances-plugin','account',item_id,account_id])), matching source inventory keys only. Transaction keys use fsi_ plus SHA256(JSON(['finances-plugin','transaction',item_id,account_id,transaction_id])). Raw IDs are transient inputs only and are not returned, stored, logged or rendered. Descriptions and account display labels must be minimized upstream; validation is not a general secret scanner. evidenceSha256 identifies the serialized preparation input, not necessarily the bytes of an original downloaded file. Raw archives and any external materialization proof remain private and separate.

Complete coverage requires every page to attest the transactions dataset, ready availability, complete/full_history state, is_complete_for_query:true, no warning codes and final has_more:false. Pagination completion alone is insufficient. A partial terminal page chain is displayable as partial, never certified complete. Query account/date scope and warnings remain visible. A source_as_of date is shown only when every page supplies the same explicit value; otherwise it stays null. collectedAt is receipt/collection time, not bank freshness. Future captures beyond five-minute clock skew are rejected.

## Minimized API and durable history

Capability: finance-source-expenses-v1. Existing paired/origin-protected GET and POST /finance/source-expenses use no-store and existing security headers. GET returns {capability,state:{revision,snapshots}}; empty state is revision 'empty' and snapshots []. Each snapshot contains schemaVersion:1, source:'finances-plugin', collectedAt, evidenceSha256, accounts:[{sourceKey,name}], query:{from,through,accountSourceKeys,includeTransfers:true}, coverage:{complete,hasMore,sourceAsOf,warningCodes}, and rows:[{sourceKey,accountSourceKey,pendingSourceKey,date,description,outflowCents,currency,pending,category:{primary,detailed,confidence},linkedTransfer}]. Null is explicit for unknown fields. Extra fields, raw identity fields, invalid dates, duplicate keys and cross-scope rows fail closed.

POST requires {capability,expectedRevision,apply,snapshot}. Use apply:false for preview, inspect the returned exact snapshot/proposedRevision, then apply:true with the same input and revision. The web client checks capability first, exact preview/receipt contents and an independent GET after apply. An uncertain write is never automatically replayed.

One worker-owned FinanceSourceExpensesStore serializes revision-checked atomic append operations into finance/source-expenses.json in the existing private worker directory. Earlier captures are immutable. Exact replay with the current revision returns existing state; a stale revision, different same-time capture or older new capture fails. Every snapshot remains separately selectable; totals never sum captures. Reads validate a bounded file and content revision; corrupt or oversized files remain untouched. Caps: 30,000 rows/100 accounts/16MB per snapshot, 200 captures/64MB total. Reaching a cap requires deliberate archival; no silent pruning. No migration, background collection, scheduler, provider write or canonical finance update exists.

## Classification and presentation

Classification uses source category enums, confidence and actual transfer linkage only. VERY_HIGH/HIGH/MEDIUM source expense categories count as provisional category-based expense or attributable credit according to sign. LOW/UNKNOWN/missing category confidence stays ambiguous unless explicit transfer linkage establishes an excluded movement. A generic purchase category conflicting with explicit cross-account linkage remains ambiguous. Only attested specific financial fee, insurance and tax details count as stronger expense evidence despite linkage, as required by the provider semantics. Supported transfers_credit_card_payment and transfers_investment_retirement_transfer_out are excluded. Unknown financial detail, BNPL repayments, other/unknown categories and unidentified inflows are not silently treated as consumption or refunds. Income never reduces spending. No generic negative-amount refund rule exists.

The latest capture appears directly under Expenses as Source récente, with Registre historique as a mutually exclusive option. Capture, month, source account and ISO currency selectors never merge datasets or currencies. Gross expense, source-attributed credits and net subtotal are shown together with category and coverage limitations. Pending and ambiguous counts are visible beside the result. An empty eligible set says Non établi rather than inferring zero; a missing rest of month is not extrapolated. Full original date-only transaction dates are preserved. Receipt timestamps use fr-CA with an explicit timezone. Source freshness is separately unknown or source-dated.

No financial source snapshots enter localStorage/IndexedDB. Failed/newer reads clear source display rather than replacing it with a misleading old total, and request generations prevent a late response from overriding a later refresh. Historical register tools and source inventory stay available without contributing to these totals.
